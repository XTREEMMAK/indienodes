# Testing fixtures

This folder is local test data. None of it ships: `testing/` is not read by the app at build or runtime, and nothing here is linked from `ring.json` at the repository root. It exists so each client (widget now, reader and field view later) has real, varied data to run against without waiting on the real submission pipeline.

`generator-assets/` is the exception to the otherwise ignored site fixtures:
it contains small, deterministic SVGs committed specifically for generator
preview and visual-regression tests. They are project-owned test art, contain
no third-party content, and must remain available in clean checkouts.

## What's here

- **`fixtures/ring.test.json`**: **50 entries**, regenerated by `scripts/generate-fixture.mjs`. The first seven are hand-written and preserved verbatim (three from real, live third-party sources; four served locally from `sites/`); the remaining 43 are generated filler, all marked `_placeholder`.

  Fifty rather than seven because a small fixture cannot exercise the things that actually break: rotation only rotates when there are more entries than nodes, shuffled-deck selection is only visibly random against a decent pool, the Settings tag list is a single line at seven entries, and link-only audio (a supported shape) needs to appear somewhere. Regeneration is deterministic, so re-running it produces no diff.

- **`sites/`**: four small static pages, each standing in for a creator's own site. Served locally (see below), each carries a `<meta name="indienode-verification">` tag matching its fixture entry's `verification_token`, so the ownership-verification flow described in the brief (section 6) has something real to check against instead of nothing.
- **`scripts/serve.mjs`**: a zero-dependency static server for `sites/`, and also for the fixture itself at `http://localhost:4174/ring.test.json` (read from `fixtures/`, with `Access-Control-Allow-Origin: *`, so a client on a different port, like the widget, can fetch it). Run `node testing/scripts/serve.mjs` (defaults to port 4174, matching the URLs already in the fixture; override with `PORT=...`).
- **`scripts/generate-fixture.mjs`**: regenerates the 50-entry fixture and the placeholder cover art in `sites/covers/`. Deterministic.

- **`ring.e2e.json`**: **committed**, unlike everything else here, because the end-to-end suite depends on it and CI has no way to generate it. Five entries — one of each type, plus a second audio entry so "next" means something — which is what the specs need to open the comic viewer, borrow the audio lane for a game trailer, and read a text entry aloud.

  It exists because those five used to live in `members/`. The suite needed them; nothing else did. That coupling meant the published ring could not be cleared for launch without turning twelve tests red, and every real deploy shipped four creators who do not exist. `src/lib/publishedRing.test.js` is the guard that keeps them from drifting back.

  No assets accompany it. Every media URL is under `https://example.invalid/`, and the specs already intercept that origin (see `route()` in `ambient-media.e2e.js`) to serve a synthetic tone and SVG, so the suite makes no real network request for entry media.

- **`scripts/seed-e2e-ring.mjs`**: copies `ring.e2e.json` over the built `ring.json` after `npm run build` and before `npm run preview` — wired into `playwright.config.js`, so `npm run test:e2e` needs nothing extra.

  It writes **two** targets. adapter-static's deployable artifact is `build/`, but SvelteKit's preview server serves its own intermediate output directory instead, whose static assets were copied from `static/` at build time. Seeding only `build/` looks like it worked — right file, right size — while the preview keeps serving the published ring.

  One consequence worth knowing: `/members` now renders twice, since the prerendered HTML carries the _published_ ring and the store then fetches the _seeded_ one. A spec that counts rows straight after `goto` sees the published ring. `members-search.e2e.js` waits for hydration for exactly this reason.

- **`scripts/fetch-xeno-audio.mjs`**: downloads the real XENO tracks for local playback. See below.
- **`scripts/refresh-bandcamp-track.mjs`**: legacy, kept for reference; the fixture no longer uses Bandcamp's expiring URLs.
- **`scripts/generate-tone.mjs`**: regenerates the two `.wav` files under `sites/driftwood-radio/`. Only needed if those files are ever deleted; the output is otherwise deterministic.

## The real-source entries

Pulled from sources the project has a legitimate reason to read: one is the site of the person who built this project, one is a public demo site, one is a real, freely-downloadable release fetched the same way a browser would. `verification_token` on all three is the literal string `test-fixture-not-verified`: this project doesn't control any of these pages, so there's no real token to check, and the value says so rather than pretending otherwise.

- **`test-audio-ashzone-xeno`**: AshZone's _XENO_, a real, free 3-track EP on Bandcamp (`ashzonemusic.bandcamp.com/album/xeno`), now played from **local copies** rather than Bandcamp's own URLs.

  Fetch them once before testing audio:

  ```bash
  node testing/scripts/fetch-xeno-audio.mjs
  ```

  Two reasons for local files. Bandcamp's streaming URLs expire in roughly 24 hours (the `ts` parameter is the expiry; an expired one returns 410), so a fixture built on them stops working overnight. And Bandcamp's CDN sends no CORS header, whereas the local test server sends `Access-Control-Allow-Origin: *`, which is what lets these files exercise the queue, finish detection, **and** the reactive background together. The remote URLs could never test that last one.

  **The downloaded audio is gitignored and must stay that way.** It is someone else's copyrighted music: holding a copy locally to test a player against real audio is fine, committing it is redistribution, which is the exact thing `docs/decisions.md` rules out for the product. Anyone who needs the files runs the script.

  **Deliberately still uses expiring `media_url`s**, unlike production. `ring.json`'s own XENO entry
  was converted to a `platform_embed` (Bandcamp's permanent EmbeddedPlayer ids, no token, no refresh),
  but this fixture keeps the direct links because it is the thing that exercises the _direct playback_
  path: the queue, finish detection, and the CORS probe all need a real `media_url` to run against.
  Expect it to need refreshing; that is what it is for.

  Bandcamp's streaming URLs are tokenized and expire. Measured rather than guessed: the `ts` query
  parameter is the expiry, the window is roughly **24 hours**, and an expired URL returns **HTTP 410**
  (a verified-expired token returned 410 while a fresh one returned 200). If playback 410s, run:

  ```bash
  node testing/scripts/refresh-bandcamp-track.mjs
  ```

  This re-fetches the album page and writes fresh `media_url` values into the fixture in place. It needs `playwright` (already a devDependency at the project root; run it from there, not from inside `testing/`), since Bandcamp's bot protection blocks plain HTTP clients and a real browser engine gets through.

  Worth knowing for later: the EP's description links to `ashzonemusic`'s own webcomic, _XenoLectric Advance_, at `tapas.io/series/XLA`. Not used here since the comic type is explicitly being figured out separately, but it's a real, live webcomic if that becomes a useful reference once that decision is made.

- **`test-text-keyjay`**: `keyjayonline.com`, used as a text-type entry rather than audio. KeyJay's real music is served from a database this fixture has no access to; the site's own bio copy and share image are real and public, which is enough to test the text card and a real `thumb_url` without needing playable audio.

- **`test-game-dinoblade`**: a real listing (title, cover image) on `fakeportal.com`, a game-discovery demo/portfolio site (not affiliated with IndieNode or the game's actual publisher). Has no `preview_url`, since fakeportal.com doesn't expose one, which also happens to test the game card's no-preview fallback.

## The local-source entries

Four fictional creators (`Driftwood Radio`, `Paper Lantern Comics`, `Loose Leaf Press`, `Tin Roof Studio`, the same names as the placeholder entries in the root `ring.json`, but not the same files) with real pages served from `sites/`, so `source_url` resolves to something real instead of `example.invalid`, and the verification flow can actually be exercised.

Start the server before using these:

```bash
node testing/scripts/serve.mjs
```

- **`test-audio-driftwood-radio`**: two generated sine-wave `.wav` files (not music, just tone), for testing the audio player and track tabs fully offline.
- **`test-comic-paper-lantern`**: three generated placeholder page images, for testing the comic reader's pagination and captions before the real comic-content question is settled.
- **`test-text-loose-leaf`**: same text sample as the production seed data, on a real local page.
- **`test-game-tin-roof`**: a generated placeholder screenshot, no `preview_url` (same fallback case as Dinoblade, but fully offline).

## Running the app against this fixture

The app reads the real `ring.json` (five entries) by default. To point it at the 50-entry fixture instead, in two terminals:

```bash
npm run fixture:serve   # serves the fixture and its assets on :4174
npm run dev:fixture     # dev server, reading the fixture instead of ring.json
```

Then open the Local URL Vite prints.

### From a phone or another device

Add `-- --host`, which exposes Vite on the network:

```bash
npm run fixture:serve
npm run dev:fixture -- --host
```

Both servers print their LAN address on startup; open the Vite one on the other device. Nothing else needs configuring, because two things adapt automatically:

- `dev:fixture` sets `VITE_RING_URL=:4174/ring.test.json`, a **port-only** value that the app resolves against whatever host the page was opened on (see `src/lib/ringStore.svelte.js`). A hardcoded `http://localhost:4174` would break here, since on a phone `localhost` is the phone.
- The fixture's own asset URLs (99 of them: covers, audio, comic pages) are stored as `http://localhost:4174` and **rewritten per request** by `serve.mjs` to match the `Host` the request arrived on. The committed file never changes and nothing needs regenerating when the network does.

A plain `npm run dev` is unaffected and still reads the real `ring.json`; production builds set nothing and read `/ring.json`.

### Optional

Fetch the real XENO audio once, if you want music instead of test tones:

```bash
npm run fixture:audio
```

Regenerate the fixture itself (deterministic, produces no diff unless the generator changed):

```bash
npm run fixture:generate
```

## Testing the widget against this fixture

The widget reads `RING_JSON_URL` from `src/lib/config.js`, which normally points at the production domain (a placeholder until launch, so it shows "ring unavailable" out of the box). To see it cycle through this fixture's seven varied entries instead of production's four sparse placeholders:

1. Start the fixture server: `node testing/scripts/serve.mjs`
2. In `src/lib/config.js`, temporarily set `RING_JSON_URL` to `'http://localhost:4174/ring.test.json'`
3. Rebuild the widget bundle: `npm run build:widget`
4. Visit `/widget` in the running app

Revert step 2 (and rebuild) before committing; it's marked `TEMPORARY` in the file as a reminder. If Bandcamp playback ever 403s mid-session, re-run `refresh-bandcamp-track.mjs` (previous section) and reload, no rebuild needed since that script edits the fixture JSON, not the widget bundle.

## A known, deliberate schema mismatch

`schema/ring.schema.json` requires `https://` on every URL, for the real product. The four local entries above use `http://localhost:4174/...`, since that's what a local static server actually serves. Running `npm run validate` (which targets the root `ring.json`, not this fixture) is unaffected. If you validate this fixture directly, expect the local entries to fail the `https://` pattern check on `source_url` and their media URLs; that's expected, not a bug, and not something to "fix" by pretending local dev has TLS.
